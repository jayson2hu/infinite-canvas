# SaaS 二次开发：安全、账户与积分结算方案

状态：**源码审查与设计建议，尚未实现**。本文不代表系统已具备注册、积分、支付、云存储或多租户能力，也不代表完成渗透测试。审查基线为 `3a6b64b602ad062b29fac66902ed18a7ef5fd9dc`。

目标用户为国内个人创作者和小团队，首版邮箱注册，预留手机号与微信身份绑定。下文的限额、时效、并发、重试、赠送额度、退款时限均为待确认产品策略；本文没有添加运行时默认值。

## 1. 结论与现有信任边界

可以保留画布、节点、素材交互和生成编排体验，但收费 SaaS 必须新建可信服务端。现有项目的主要模式是“用户在自己浏览器保存自己的 API Key，浏览器直接请求供应商”。用户能够修改浏览器状态、请求和脚本，因此浏览器余额、前端扣分或前端返回的成功状态都不能作为计费依据。

`canvas-agent` 是带本地文件及 CLI 能力的个人计算机服务，`canvas-proxy` 是解决本地跨域的转发工具；两者均不应直接改成公网共享服务。当前默认仅监听回环地址是保护边界，不能将该边界删除后宣称具备服务器安全性。

## 2. 首版必须改变的产品边界

保留画布、基础素材库、经审核的模板、平台模型目录、生成历史和导出。对普通用户关闭渠道 API Key/Base URL 配置、模型脚本编辑和执行、远程插件安装和启动、本地 Agent、本地 Proxy、任意 WebDAV 凭证配置。原有个人自托管能力如需保留，可作为独立构建模式，不与平台付费会话共用未经隔离的执行环境。

后续插件可以先采用经过审核并随版本发布的内置节点。即使供应商 Key 已移到服务端，主页面任意脚本仍能用登录用户身份创建收费任务；`HttpOnly` Cookie 无法单独解决这种问题。第三方脚本重启前应设计独立来源沙箱、明确能力接口、宿主授权及签名版本校验。

管理员可管理模型和供应商，但前端提交 `model_id` 与允许参数，不提交 `baseUrl`、上游路径、鉴权头、执行代码、用户余额或最终价格。服务端必须校验模型状态、允许的尺寸/时长/数量、素材权限、用户资格与报价。

## 3. 注册、登录与账号合并

首版统一采用邮箱验证码注册与免密登录，降低国内用户对海外身份提供商的依赖。验证码由服务端使用密码学安全随机源生成，与邮箱、用途和请求上下文绑定，使用带服务端密钥的摘要保护存储，限定有效期、验证尝试和单次消费；短验证码不能仅依赖无密钥摘要抵御离线枚举。验证成功后的会话签发、首次注册和赠分分别使用事务及幂等约束，避免重复验证重复发放。上线前验证国内邮件送达率与发送成本。密码登录和密码重置留待明确需求后设计，不纳入首版。

- `users` 存内部用户标识和账户状态；`auth_identities` 存邮箱、手机号、微信身份及验证状态。身份表对身份提供方与其主体 ID 设置唯一约束，不把邮箱/手机号作为业务表主键。
- 邮箱规范化采取保守规则；不要跨服务商随意移除点号、加号后缀导致合并不同身份。微信按应用范围处理 OpenID；UnionID 仅在实际满足平台条件时用于关联。
- 绑定手机号、微信或更换邮箱需验证新身份，并验证当前账号控制权；同一手机号/微信已有账号时走显式合并或转移流程，不静默合并钱包。
- 会话建议使用服务端可撤销的安全 Cookie，设置 HttpOnly、Secure、适当 SameSite；状态变更接口同时校验 CSRF/请求来源。身份变更、封禁和风险事件撤销相关会话。
- 注册、验证码发送、验证尝试和登录分别做速率与成本控制，使用账号、IP、设备信号及行为组合。IP 不是身份，避免同一公司网络整体误封。
- 新手积分只在邮箱验证且满足风控条件后发放，`(user_id, campaign_id)` 唯一；同时明确每个真实用户的活动资格。多账号、临时邮箱与批量脚本应进入风控，不把“每封邮箱一次”当作防刷保证。
- 邮箱存在与否采用一致的外部响应，记录内部风控事件；日志不保存验证码、密码、完整令牌或供应商鉴权信息。
- 管理员与普通用户权限分开，管理员要求额外验证，手工发分/扣分/退款必须记录操作人、原因和关联工单。

## 4. 租户与素材隔离

首版仅开放个人工作区和个人积分，不开放团队共享钱包。数据结构预留 `workspace_id` 与成员关系，后续有明确需求时再开放小团队共享、角色管理和团队钱包。未来团队钱包需独立于个人钱包，报价明确显示付款工作区，禁止静默混用余额。

每个项目、素材、任务、报价、钱包和订单必须有确定归属。API 从已认证会话确定当前用户，在服务端检查该用户对目标工作区的权限；不能信任请求体的 `user_id`/`workspace_id`。所有通过 ID 读取、更新、下载、取消、导出、查询进度的入口均要校验归属。随机 ID、签名 URL 和前端路由守卫均不能替代对象授权。

数据库查询约束租户范围，关键表使用包含租户 ID 的关联约束，避免把 A 工作区任务关联到 B 工作区素材。可增加 PostgreSQL 行级安全作为纵深防御，但必须验证应用连接角色和后台任务不会绕过策略。队列 Worker 同样执行任务与素材归属检查。

对象存储默认私有，上传地址只能写入预分配的对象键，完成后由服务端验证实际文件类型、尺寸与归属；下载临时签名地址必须先授权。文件名与扩展名不决定安全性，处理图片解码炸弹和超大视频，SVG/HTML 等可执行内容不得在应用来源直接渲染。具体大小、数量、时长和配额经产品确认再配置。

浏览器缓存按 `user_id/workspace_id` 分区，退出时清理当前会话内存与敏感缓存。无账号的旧本地画布首次进入云工作区时需显式选择导入，不能自动将同设备旧数据视作新登录账号所有。画布编辑保存使用 revision/ETag 冲突检测，避免多标签页或多设备静默覆盖。

## 5. 积分账本和报价

积分是平台服务消费单位，不应在界面上混同现金余额。使用整数最小单位，人民币订单金额使用整数“分”，供应商成本使用明确币种和定点数；禁止 JavaScript 浮点金额直接入账。明确购买积分、赠送积分、有效期、抵扣顺序和退款规则，并在购买时展示。首版建议先不引入复杂过期机制；若采用赠分到期，必须建立批次及冻结分配，不能只在钱包加一个到期日期。

余额不是一个可任意编辑的字段。建立追加式流水，任何充值、赠送、冻结、消耗、解冻、退款和人工调整均有原因、关联对象、幂等标识与余额变化。纠错追加反向流水，不修改历史记录。钱包汇总在同一数据库事务中更新，并能用流水独立重算。

建议的最小数据实体：

| 实体 | 关键内容与约束 |
| --- | --- |
| `wallets` | 工作区、可用积分 `available`、冻结积分 `held`、版本；二者不得小于零 |
| `credit_ledger` | 操作类型、可用/冻结增减、关联订单/任务/冻结记录、操作者、说明；业务操作幂等唯一 |
| `credit_reservations` | 一次收费操作的冻结额、状态、冻结分配；一个任务绑定一个冻结主体 |
| `price_versions` / `quotes` | 模型、供应商映射版本、参数、价格版本、最大积分、可接受时效、所属工作区 |
| `generation_jobs` / `job_attempts` | 任务状态、输入摘要、报价、供应商请求 ID、尝试状态、交付资源；客户端幂等键在工作区内唯一 |
| `payment_orders` / `payment_events` | 人民币订单金额、购买积分、商户、支付渠道交易 ID、验签事件和履约状态 |
| `outbox_events` | 与钱包冻结、任务创建同事务写入，提交后可靠投递队列 |

报价应由服务端产生，绑定规范化参数摘要、价格版本、工作区与允许的最高消耗。用户点击生成时提交 `quote_id` 和幂等键，服务端重新验证绑定关系；前端自改价格、数量或模型必须失效重报。价格调整不影响已接受的报价。新手试用、套餐、折扣也由服务端策略计算并留痕。

先采用清楚的按张、按时长档位或固定任务价格。成本跟踪单独记录上游实际计费，避免把供应商原始成本直接暴露为用户价格。需要 token 按量计费时，创建任务前冻结可计算的最高金额并限制输入/输出预算；超出报价上限不能事后任意加扣。

## 6. 原子冻结与可靠结算

推荐状态为 `queued → dispatching → running → succeeded/failed/cancelled`，另有 `reconciling` 表示供应商结果不确定；账务终态与任务终态在同一事务中落地。`cancel_requested` 仅代表用户请求取消，不代表供应商确认取消或免单。

1. **受理：**验证用户、工作区、输入素材和报价。数据库事务内创建/读取客户端幂等请求，锁定钱包或使用条件更新；仅当 `available >= Q` 才将可用积分减 `Q`、冻结加 `Q`。写冻结流水、任务、冻结记录和 outbox，整体提交。任一失败整体回滚。
2. **派发：**Worker 通过受约束状态迁移取得执行权，使用稳定的供应商幂等键（若供应商支持），保存上游请求 ID。不在数据库事务内等待外部生成。
3. **交付成功：**保存并验证可读取的结果素材后，以数据库事务锁定未结算冻结记录。实际确认计费为 `C` 且 `C <= Q`，冻结减 `Q`、可用增加 `Q-C`，追加消耗/余量退回流水，记录交付和结算终态。
4. **确定失败或受理前取消：**冻结减 `Q`、可用加 `Q`，写解冻流水。重复回调、轮询、恢复任务只能首次生效。
5. **不确定：**请求超时、网络断连、Worker 崩溃后无法确认上游是否接单，进入对账状态。先按请求 ID 查询/恢复，不立刻解冻并再次派发；否则可能出现一次收款、多次上游消耗。

幂等必须依赖数据库唯一约束和事务：同一个工作区与幂等键重复、且参数摘要相同，返回原任务；相同键换参数返回冲突。Redis 锁和禁用按钮只能辅助，不能保证财务正确性。回调和轮询竞争结算时，只有持有未结算记录的一方能够提交。

在“不支持幂等或查询”的供应商上，请求发出后发生未知结果，不能声称实现端到端 exactly-once，也不应自动切换另一供应商重试。应保留不确定状态、告知用户并提供人工处理入口；对账处理时限与最终补偿策略上线前确认。系统确需自动重试时，应限定为可证明尚未受理或可安全复用上游幂等键的阶段。

浏览器关闭、切换页面、停止前端轮询或 SSE 断开，均不代表后端任务取消。恢复页面后读取服务端任务与账务状态；前端不得自行解冻。对于流式文本，已交付部分的收费与用户中止规则必须预先明确；图像/视频首版更适合按成功交付结算。

批量生成按可独立交付的子任务报价与分配冻结：例如三张只成功两张，则只结算两张，其余确定失败后解冻。因上游一次性整批计费产生的差额属于平台成本策略，不可悄悄转嫁为用户“失败扣费”。供应商成功但转存失败时先恢复下载，不再次生成；在最终不能交付时按事先公布的用户规则退款/补偿，另记平台供应商成本。

退款到原积分来源。赠送、付费、过期批次存在时，冻结/释放记录必须保留来源，避免失败退回把赠送积分变成可退款付费积分，或把已到期赠分变成永久余额。

## 7. 支付、退款与对账

付费充值可接符合运营主体条件的微信支付/支付宝商户接口。先验证主体、商户开通和收款能力，再承诺上线充值。不要用个人收款码加前端“已支付”按钮作为自动发分依据。

- 服务端创建固定金额、币种、积分数和优惠规则的订单；客户端只选择套餐，不决定最终金额。
- 回调验证渠道签名/证书、商户和应用身份、平台订单号、渠道交易号、实付金额、币种及真实支付状态。使用渠道 SDK 或成熟验签实现，并按渠道要求解密回调。
- 对渠道事件做去重，对渠道交易号设置唯一约束；更关键的是对订单发分设置唯一履约约束。不同事件 ID 的重复成功通知也只能发一次积分。
- 验签成功不等于已持久化：将支付确认、订单履约、钱包加分、流水与后续事件写入同一事务；提交后返回成功应答，数据库失败让渠道重试。
- 用户浏览器支付成功跳转只触发查单，不发积分；主动渠道查单和回调共用同一结算入口。
- 订单本地过期后收到真实支付成功，仍按明确规则发分或进入原路退款流程；不能直接丢弃已付款订单。
- 退款需区分付费积分与赠分、已消费与冻结部分；同事务冻结/扣回可退款积分后向渠道发起退款，记录退款状态并查询确认，不能把“提交退款请求”当作“退款已到账”。
- 订单/渠道账单/钱包流水/供应商用量分别对账，保留差异队列；后台能查看冻结来源、上游请求、重试次数和账务事件，处理补单必须幂等。

## 8. 自有后端部署边界

建议前端和 API 同站点经 HTTPS 入口服务；后端 API、Worker、PostgreSQL、队列和私有对象存储分工明确。首版模块化单体即可，避免先引入大量微服务。公网仅开放必要 Web/API 入口，数据库、队列和管理接口不直接公网开放；Worker 不共享个人电脑的 Agent 工作区或登录凭证。

供应商密钥、邮件凭证、支付私钥只在服务端密钥管理或运行环境中提供，不放 Vite 构建变量、`config.js`、仓库、镜像层、前端错误或浏览器存储。生产、测试使用不同凭证，支持轮换，日志默认脱敏并按权限访问。

后端只访问经管理配置的供应商目标；禁止用户提交任意上游 URL。远程参考素材导入如确需支持，需要防 SSRF：允许协议与域名、校验 DNS 解析与实际连接目标、拒绝内网/回环/链路本地/云元数据地址、逐跳重新校验重定向、限制下载资源。配合网络出站策略阻止访问内网，不能仅靠 URL 字符串正则。

上传、并发任务、单任务成本、账户日消耗、队列深度、供应商预算、邮件发送均需可配置控制；当供应商余额、错误率或成本异常时可关闭模型并保留已受理任务的结算路径。具体阈值应结合实际供给和价格确认，不在原型中静默硬编码。

上线前需要数据库备份及恢复演练、对象存储恢复策略、任务重启恢复、凭证轮换、日志脱敏和故障补单手册。对于国内对外服务，应按实际部署地区、经营主体、生成内容功能与数据流向核对备案、隐私告知、内容治理、生成内容标识及模型供应商要求；此处是产品与工程核对范围，不等于已完成合规结论。

## 9. 上线验收门槛

这些是后续实现所需测试与验收，**本次均未执行**：

- 两个账号分别尝试读取、下载、取消、导出对方的项目、素材、任务和订单；API 与队列都必须拒绝越权。
- 同浏览器切换账号，不显示上一账号的私有素材；未登录旧数据导入不会隐式归属他人。
- 对不足额钱包并发受理多个任务，只接受余额覆盖的任务，余额与冻结不可为负，流水可独立重算。
- 重复点击、同键换参数、队列重复投递、乱序回调、轮询和回调同时到达，均不重复调用或结算；未知上游受理状态走对账。
- 在冻结事务提交、队列发布、供应商接单、结果落存、结算提交各阶段模拟进程退出；恢复后没有丢任务、双扣款或永久无解释冻结。
- 生成成功、部分成功、审核拒绝、排队取消、受理后取消、浏览器关闭、下载失败、供应商超时，账务按已公布规则一致处理。
- 伪造支付回调、错误金额/商户/币种、重复通知、先失败后成功、成功跳转但未付款，不错误发分；真实延迟支付能履约或退款。
- 首版前端产物与浏览器请求中没有平台 Key；URL、诊断信息、日志和对象存储元数据不泄露密钥。
- 所有自定义脚本和外部插件执行入口确实关闭，包括缓存恢复、配置导入和本地插件发现；隐藏按钮不视为通过。
- 私有存储未公开，外部资源导入不能访问内网/云元数据；数据库和队列无法从公网直接访问。
- 备份能恢复，供应商故障能停止受理并保留已受理任务，财务能追踪每笔资金与积分变化。
